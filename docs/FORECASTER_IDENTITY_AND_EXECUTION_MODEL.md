# Forecaster identity, agent, model, and execution architecture

Status: current Forecast Library design contract
Version: 1.0
Last reviewed: 2026-08-28

## Core distinction

Not every node in the Forecast Library knowledge graph represents an
independently existing real-world entity.

| Scope | Examples | External identity links |
| --- | --- | --- |
| `global` | PepsiCo, an active listed security, Future Edge Group FZE, a verified human forecaster | May use governed Wikidata, official website, Wikipedia, or other `sameAs` links |
| `platform` | iPulse AI Research team, an iPulse AI forecaster profile | Uses a stable Forecast Library/iPulse identifier; normally has no external `sameAs` |
| `configuration` | Analyst mode, task configuration, subject assignment | Identified by the source configuration ID and version; never presented as a person or organization |
| `event` | One forecast execution, one forecast receipt, one proof | Identified by immutable forecast, receipt, and proof identifiers |

An AI forecaster profile named after or inspired by a known person is a
`platform` entity. It must not use the namesake person's Wikidata ID, Person
entity, image rights, or `sameAs` links. A genuinely verified human forecaster
may be linked to a separate `global` Person entity.

## iPulse AI mapping

```text
Publisher organization
  Future Edge Group FZE
    -> product/team: iPulse AI Research
      -> forecaster profile: ai_analysts.analyst_id
        -> persona: analyst_personas.persona_id
        -> exact model specification/version
        -> task configuration: ai_task_configs.task_config_id
          -> mode: ai_analyst_modes.analyst_mode_id
          -> prompt, input, output, tools, horizon and cadence
          -> subject assignment: xref_subject_task_config_charging.xref_id
            -> forecast execution: forecast_id + batch/run time
              -> Open Forecast Receipt
                -> optional blockchain proof
```

### Identity rules

1. `analyst_id` is the stable iPulse forecaster-profile ID and maps directly to
   `forecasterProfileId` in Forecast Library. The analyst definition includes its persona,
   archetype/investment framework, and exact model specification/version. For
   example, **Ray Dalio AI on Gemini 3.1 Pro** is one complete iPulse AI
   forecaster profile; "Ray Dalio AI" alone is only its persona-facing label.
2. Mode is not part of forecaster identity. The same forecaster profile may run
   in THINKER, RESEARCHER, SCHOLAR, or future modes.
3. A task configuration is the reusable execution definition. It binds the
   already model-specific forecaster profile to a mode and the relevant prompt,
   API/runtime settings, tools, input and output formats, horizon, cadence, and
   other configuration. It must not silently replace the model that defines the
   analyst. A different model specification/version requires a distinct or
   explicitly versioned analyst profile.
4. An xref record is a reusable assignment of a subject/entity to a task
   configuration. It is not an individual forecast.
5. A forecast is one execution output from an assignment in a particular batch
   or run. It receives its own forecast ID and receipt.
6. Review belongs to a forecast or receipt, not permanently to the forecaster.
7. A forecast receipt never owns or requires a portrait. A public forecaster
   profile may reference optional governed `profileMedia` such as an official
   human avatar, organization logo, or publisher-owned generated mark. The
   media remains presentation metadata outside the sealed forecast identity.
8. Platform AI personas inspired by real people must not display the namesake
   person's photograph or imply endorsement. Use a neutral type mark or a
   publisher-owned generated mark instead.
9. Charts, maps, screenshots, and other forecast-related media are evidence or
   attachments, not forecaster portraits. Reference them by digest, media type,
   byte length, access policy, and optional URI; do not embed binary media in
   the receipt.

### Public ledger type

The Library presents one clear execution class beside every forecast:

- `Human` - generated by an identified human forecaster;
- `AI` - generated by an AI model, AI agent, hybrid AI workflow, or AI ensemble;
- `Quant Model` - generated by a deterministic algorithm, statistical model,
  econometric model, or other traditional quantitative system.

This three-value display classification does not replace the more detailed
`forecaster.type` stored in the receipt. Organizations and teams remain the
publisher, owner, or accountable party; they are not a fourth execution class.

The public profile is an index. Each individual forecast receipt freezes the
exact forecaster, model, mode, task configuration, input/output lineage, review,
and temporal boundaries used for that forecast.

`publishedSubjectCategories` is a structured list of governed entity/subject
categories the forecaster has actually covered in published receipts, such as
`equity`, `crypto`, or `index`. The UI may present the array as a comma-separated
label, but the stored value remains an extensible list rather than a free-form
string. This field records demonstrated public coverage, not an asserted area
of expertise or the broader configured applicability of the analyst and its
task configurations.

Configured applicability is a separate concept. When an iPulse AI adapter
publishes it, it should come from the governed analyst and task-configuration
records; a null analyst category filter means universal applicability. It must
not be inferred from the categories happened to appear in published receipts.

## Architecture decision

Forecast Library will use a **Forecaster Card** as its universal, comparable
identity contract. A Forecaster Card can describe a human, an AI system, a
traditional quantitative model, an ensemble, a hybrid process, or an
institutional forecaster.

An A2A Agent Card is not the universal card. It is an optional service binding
for a forecaster implementation that is actually exposed as an A2A server.

This separation is mandatory:

```text
Actor or accountable party
  -> Forecaster Card
    -> immutable Forecaster Version
      -> optional callable Service
        -> optional A2A Agent Card version
      -> Forecast Run
        -> Forecast
          -> Open Forecast Receipt
            -> optional Proof
            -> later Evaluation
```

The design prevents four common category errors:

1. A base model is not automatically an agent.
2. A persona plus a model is not automatically an agent.
3. A single model invocation is a run, not an agent identity.
4. An A2A Agent Card advertises a callable service; it does not prove which
   model, prompt, tools, evidence, or execution path produced a forecast.

## Canonical vocabulary

| Term | Precise meaning | iPulse AI example |
| --- | --- | --- |
| Actor | A person, organization, team, or software system participating in authorship, operation, review, or publication | Future Edge Group FZE; iPulse AI Research; a named human reviewer |
| Model | Weights or an algorithm that maps inputs to outputs | Gemini 3.1 Pro; an ARIMA model |
| Persona | A governed perspective, method, cognitive style, or investment framework | Warren Buffett-inspired value-investing persona |
| Forecaster Card | Stable public identity and governance record for something authorized to issue forecasts | Warren Buffett AI on Gemini 3.1 Pro |
| Forecaster Version | Immutable implementation snapshot of a Forecaster Card | Persona version + model version + method/policy versions |
| Task Template | Reusable instruction and I/O contract for a class of work | iPulse AI task configuration |
| Subject Assignment | Reusable binding between a governed subject and a task template | iPulse AI subject-task xref |
| Service | Optional callable software endpoint implementing a forecaster or forecasting capability | Future iPulse AI Forecasting Service |
| Agent | A goal-directed software system that manages task state and can adaptively choose or sequence actions from intermediate state | A bounded research agent that searches, evaluates evidence, revises, and terminates |
| A2A Agent | An agent or agentic system exposed through the Agent2Agent protocol | An A2A server with an Agent Card and task endpoint |
| Run | One concrete execution with actual inputs, configuration, tools, timestamps, and result | One Batch 6 THINKER invocation |
| Forecast | The predicted values or probabilities produced by one run | A 20-step price-return path |
| Receipt | The immutable forecast plus the provenance needed to inspect it | Open Forecast Receipt |

### The current iPulse AI analyst is not automatically an agent

The current iPulse AI definition is:

```text
AI Analyst = Persona + exact Model specification/version
```

That is a strong definition of a configured AI forecaster. It should remain
the source-system term because iPulse AI analysts also perform investment
research. In Forecast Library it maps to an `ai_system` Forecaster Card.

For example, **Warren Buffett AI on Gemini 3.1 Pro** is a complete configured
AI forecaster identity. It is not merely a label for Gemini, and it is not the
real Warren Buffett. It should be described as a publisher-defined,
Warren-Buffett-inspired AI forecaster with no identity link, portrait, or
endorsement claim involving the real person.

Whether a specific run is agentic is recorded separately. On the current
evidence:

| iPulse AI mode | Control flow | Context acquisition | Agentic? |
| --- | --- | --- | --- |
| THINKER | `single_model_invocation` | Supplied input snapshot; no external retrieval configured | No |
| RESEARCHER | `single_model_invocation` in the current pipeline | Web search may be configured; actual execution is recorded separately | No, unless the application adaptively loops over intermediate results |
| SCHOLAR | `single_model_invocation` or `fixed_sequence`, depending on the pipeline | RAG retrieval may be configured; actual retrieval is recorded separately | No, unless the application adaptively loops over intermediate results |
| Future planner/tool loop | `adaptive_loop` | Any declared channels | Yes |
| Future communicating agent team | `multi_agent_orchestration` | Any declared channels | Yes |

The words `THINKER`, `RESEARCHER`, and `SCHOLAR` remain iPulse AI operating
modes. They do not become universal Forecast Library forecaster types.

## Orthogonal run classification

A single enum cannot accurately describe producer identity, control flow,
context acquisition, and provider submission mechanics. Forecast Library keeps
these dimensions separate.

### Dimension 1: producer and implementation

`forecasterKind` and `implementationKind` answer **what produced the
forecast**. Examples include a human, configured LLM forecaster, statistical
model, agent, ensemble, or hybrid. These belong to the Forecaster Card and its
immutable version.

### Dimension 2: control flow

`controlFlowPattern` answers **how the run was orchestrated**:

| Value | Meaning |
| --- | --- |
| `single_model_invocation` | One application-level model or inference invocation produces the result |
| `fixed_sequence` | Multiple predefined stages run in a fixed order without adaptive planning |
| `adaptive_loop` | Intermediate state determines which action to take or whether another iteration is required |
| `multi_agent_orchestration` | Multiple separately identified agents communicate, delegate, or adjudicate |
| `human_process` | A human or governed human process creates the forecast; its detailed method belongs to the human profile |

A run is normally `agentic: true` only for `adaptive_loop` or
`multi_agent_orchestration`. Tool use alone does not make a run agentic.
Calling a model through an API does not make the model an A2A agent.

The word `turn` is avoided in the canonical enum because it can mean a chat
message, a model API call, a workflow stage, or an agent iteration. Objective
counts such as `modelInvocationCount`, `retrievalOperationCount`, and
`toolInvocationCount` remove that ambiguity.

### Dimension 3: context acquisition

Retrieval is an input/provenance dimension, not a control-flow pattern. A
single invocation, fixed sequence, or adaptive loop may use any combination of:

```text
supplied_input_snapshot
bigquery_or_database
web_search
rag_retrieval
external_api
tool_output
human_supplied_evidence
```

Each channel records configured and actual state separately:

```json
{
  "channel": "web_search",
  "configured": true,
  "acquisitionStage": "in_run",
  "actualStatus": "executed",
  "operationCount": 3,
  "evidenceManifestDigestSha256": "..."
}
```

`actualStatus` is one of `executed`, `not_executed`, `unknown`, or
`not_applicable`. Configured capability is never treated as proof that a channel
actually ran. `acquisitionStage` distinguishes context prepared before the model
invocation from retrieval performed during the run; recommended values are
`pre_run`, `in_run`, `human_preparation`, and `unknown`.

Retrieval therefore does not tell us whether a workflow was single-invocation,
fixed, or agentic. A single model invocation can consume a prepared RAG snapshot
or invoke provider-side search. A fixed sequence or adaptive loop can use the
same channels. Only application-visible sequencing and adaptation determine the
control-flow classification.

### Dimension 4: submission and response mechanics

Immediate versus provider batch submission, synchronous versus deferred
response, and retry count are operational transport facts. They do not describe
reasoning or agenticity. The existing iPulse AI `prediction_approach = batch`
means Gemini Batch API packaging, not a multi-step or agentic forecast.

Recommended fields are `requestSubmissionMode`, `responseDeliveryMode`, and
`retryCount`. The existing `prediction_approach` field should not be reused as
the semantic control-flow classification.

## Where the metadata belongs in iPulse AI

| Layer | Stores | Does not store |
| --- | --- | --- |
| `ai_analysts` | Stable configured forecaster identity: persona + exact model | Per-run mode, retrieval execution, or run result |
| `ai_analyst_modes` | Reusable capabilities and policies: web search enabled, RAG enabled, retrieval intensity, model/tool parameters | A claim that search or retrieval actually executed |
| `ai_task_configs` | Declared `controlFlowPattern`, mode reference, prompt assembly, I/O contract, horizon, and task-level execution policy | Subject-specific assignment or actual run telemetry |
| `xref_subject_task_config_charging` | Subject-to-task assignment, frequency, access, and charge overrides | Duplicated forecaster or orchestration metadata, except a rare explicit subject-specific override |
| `prediction_status` | Canonical per-run actual snapshot: declared and actual control flow, context channels, counts, execution evidence, classification source, and confidence | Full raw prompts/responses in compact catalog projections |
| Full prediction/output records | Forecast values and detailed output, linked to the run | Mutable profile definitions |
| Forecast Library materialized records | Public compact projection of the run and receipt | Secrets or guessed telemetry |
| Open Forecast Receipt v0.2 | Immutable public projection of exact forecaster version and actual disclosed run provenance | A complete mutable Forecaster Card or credentials |

The durable BigQuery design should add a typed JSON
`execution_provenance` column to `prediction_status` through a new forward
Liquibase changeset. It should also add a declared `control_flow_pattern` to
`ai_task_configs`. The shared Pydantic models and local/remote schema registries
must be advanced in the same release. Existing executed changesets remain
immutable.

This is deliberately not one attribute on one table. The declared and actual
facts have different owners:

```text
ai_task_configs.control_flow_pattern
  = intended reusable orchestration

ai_analyst_modes.web_search / rag_search / retrieval policies
  = reusable configured context capabilities

prediction_status.execution_provenance
  = point-in-time evidence of what this run actually did

xref_subject_task_config_charging
  = assignment only; no duplicated orchestration or retrieval metadata
```

### Native capture and historical backfill

"Capture in future runs" means native capture should become the default; it
does not mean historical runs are excluded. Existing runs, including Batch 6,
should be backfilled wherever the source evidence supports an exact statement.

Backfill uses this evidence order:

1. per-run grounding, retrieval, or tool telemetry;
2. the immutable input snapshot and its component or evidence manifests;
3. the referenced, versioned analyst mode and task configuration;
4. the exact pipeline/code version that executed the run.

Do not infer execution from a display label such as `RESEARCHER`, from a model's
general capability, or from the mere presence of a URL in generated prose.

| Historical fact | Backfill rule |
| --- | --- |
| Declared web/RAG capability | Copy from the referenced analyst-mode version |
| Actual web-search execution | `executed` only when grounding/tool telemetry proves it; otherwise `unknown` |
| Pre-run context | `executed` when the run references an input snapshot; preserve its digest and effective cutoff |
| Actual RAG retrieval | `executed` only when a retrieval/input-component manifest proves it; otherwise `unknown` |
| Control flow | Classify from the versioned pipeline definition and run telemetry, not from provider batch transport |
| Submission mechanics | Backfill from existing approach, response-generation, batch, retry, and timing fields |

Every enrichment records `capture.mode`, classification time, evidence sources,
and confidence. The backfill may populate `prediction_status.execution_provenance`
and the Forecast Library read model, but it must never rewrite a sealed v0.1
receipt payload or change its digest. Open Forecast Receipt v0.2 will capture the
same fields natively at issuance.

types and broad enough to support type-specific extensions.

### Common fields

Every Forecaster Card has:

- stable `forecasterId` and immutable version references;
- `forecasterKind`;
- public name and description;
- accountable party and, where applicable, operator team;
- status, verification, disclosures, and source-system references;
- governed specializations and supported target/domain categories;
- supported control-flow patterns;
- optional public methodology and documentation links;
- optional type-specific profile reference;
- optional service bindings.

Recommended `forecasterKind` values:

```text
human
ai_system
quantitative_model
ensemble
hybrid
organization
```

Recommended `implementationKind` values include:

```text
human_judgment
configured_llm_forecaster
deterministic_algorithm
statistical_model
machine_learning_model
workflow_system
agent
multi_agent_system
weighted_ensemble
hybrid_human_ai
institutional_process
```

The two levels are intentional. For example, an `ai_system` may be implemented
as a `configured_llm_forecaster`, `agent`, or `multi_agent_system`.

## Type-specific profiles

### Human forecaster profile

A human profile is comparable to an AI or quantitative profile without
pretending to be software:

- verified person identity or publisher-scoped pseudonym;
- affiliations and represented organization or team;
- declared specializations and methodology;
- credentials and optional ORCID or official profile links;
- jurisdiction where voluntarily and lawfully disclosed;
- conflicts, sponsorships, and disclosure policy;
- public track-record scope;
- review and publication governance;
- optional profile media with explicit rights metadata.

Knowledge boundaries for humans are declared, unknown, or evidence-based. They
must never be fabricated as a model-style cutoff date.

### Quantitative or traditional ML model profile

This profile follows the spirit of Model Cards rather than Agent Cards:

- algorithm/model family and intended use;
- authors, owner, and operator;
- stable artifact, code, and version identifiers;
- training or estimation window;
- training-data and feature-schema references or digests;
- input and output contracts;
- target, unit, cadence, and assumptions;
- validation method and reported metrics;
- limitations, known failure modes, and out-of-scope uses;
- code commit, container digest, dependency, and runtime versions when known;
- license and access policy;
- inference interface, if one exists.

A statistical model remains `quantitative_model` even if a service wraps it.
It becomes part of an `agent` only when an agentic system controls how and when
it is used.

### AI system profile

The AI profile records:

- persona or method definition and version;
- base-model specification and exact version;
- provider and API identifier;
- prompt-policy, tool-policy, retrieval-policy, memory-policy, framework, code,
  and output-schema versions;
- knowledge-boundary source and precision;
- supported control-flow patterns;
- architecture authors and accountable operator;
- safety, limitations, and human-oversight policy;
- optional service and A2A bindings.

### Ensemble and hybrid profiles

These profiles reference their members instead of copying their identities:

- member Forecaster Card version IDs;
- role and weight, if fixed;
- aggregation or adjudication method and version;
- missing-member and disagreement policy;
- human approval or override policy;
- whether the public output is a new forecast or a summary of member forecasts.

An iPulse AI consensus average is an aggregation product, not a substitute for
the twelve individual forecasts. It can have its own ensemble Forecaster Card
only when its method and version are explicit.

## A2A Agent Card integration

The A2A 1.0 specification defines an Agent Card as a discovery manifest for an
A2A server. Its required public information includes agent name, description,
version, supported interfaces, capabilities, default input/output media types,
and skills. It can also describe provider, security, documentation, icon, and
signatures. The well-known discovery URL is:

```text
https://{agent-domain}/.well-known/agent-card.json
```

Forecast Library must not invent an A2A Agent Card for a non-callable persona,
human, or model. An A2A binding is present only when all of these are true:

1. a live service implements an A2A protocol binding;
2. it exposes a task or message interface;
3. it publishes a conforming Agent Card;
4. the relevant Forecaster Card is governed as the implementer or capability
   behind that service;
5. a forecast run can record the actual service/card version used.

The A2A card remains owned by the service. Forecast Library stores a versioned
reference and integrity snapshot:

```json
{
  "bindingType": "a2a",
  "serviceId": "fl_service_ipulse_forecasting",
  "agentCardUrl": "https://agents.ipulseai.com/.well-known/agent-card.json",
  "a2aProtocolVersion": "1.0",
  "agentCardVersion": "1.2.0",
  "agentCardDigestSha256": "...",
  "agentCardRetrievedAt": "2026-08-28T12:00:00Z",
  "signatureStatus": "verified",
  "archivedSnapshotUri": "https://forecastlibrary.com/api/v1/agent-card-snapshots/..."
}
```

Never store API keys, OAuth tokens, private endpoints, or other credentials in
a Forecaster Card, receipt, Agent Card snapshot, or public Firestore document.

### Recommended future iPulse AI A2A shape

Do not create twelve misleading A2A cards merely because there are twelve
iPulse AI forecaster profiles. The first sensible A2A implementation is one
**iPulse AI Forecasting Service** that advertises governed skills such as:

```text
generate-market-forecast
inspect-forecast-method
retrieve-public-forecast-receipt
verify-forecast-receipt
```

If a particular iPulse AI forecaster later becomes an independently callable,
stateful agent with its own task lifecycle, it may receive its own card or a
governed tenant-specific interface. Until then, its Forecaster Card references
the configured implementation and its runs, not an imaginary A2A service.

The actual execution belongs to the run, not the profile. Each run records:

```json
{
  "runId": "fl_run_...",
  "forecasterId": "fl_forecaster_...",
  "forecasterVersionId": "fl_forecaster_version_...",
  "controlFlowPattern": "single_model_invocation",
  "agentic": false,
  "sourceMode": "THINKER",
  "taskTemplateId": "taskconfig_...",
  "subjectAssignmentId": "xrefsubjtskconf_...",
  "modelVersionIds": ["aimodelversion_..."],
  "modelInvocationCount": 1,
  "retrievalOperationCount": 0,
  "toolInvocationCount": 0,
  "contextChannels": [
    {
      "channel": "supplied_input_snapshot",
      "configured": true,
      "acquisitionStage": "pre_run",
      "actualStatus": "executed"
    }
  ],
  "inputSnapshotDigestSha256": "...",
  "promptDigestSha256": "...",
  "startedAt": "2026-07-05T14:55:40Z",
  "completedAt": "2026-07-05T14:56:47Z",
  "serviceInvocation": null
}
```

For an A2A-mediated run, `serviceInvocation` adds only the verifiable invocation
metadata needed for provenance:

```json
{
  "protocol": "A2A",
  "protocolVersion": "1.0",
  "serviceId": "fl_service_...",
  "agentCardDigestSha256": "...",
  "interfaceBinding": "HTTP+JSON",
  "skillId": "generate-market-forecast",
  "taskId": "a2a-task-...",
  "contextId": "a2a-context-..."
}
```

Task and context identifiers may be withheld from the public receipt when they
would expose private operational information. Their salted or namespaced digest
may be disclosed instead.

## Receipt projection

The receipt should not embed a complete mutable profile, model card, or Agent
Card. It freezes a compact point-in-time projection and references immutable
versions:

```json
{
```

## Firestore source and read model

Use normalized governed records for identity and materialized catalogs for
cheap public reads:

```text
public_actors/{actorId}
public_forecasters/{forecasterId}
public_forecaster_versions/{forecasterVersionId}
public_model_profiles/{modelProfileId}
public_model_versions/{modelVersionId}
public_services/{serviceId}
public_agent_card_versions/{agentCardSnapshotId}
public_forecast_runs/{runId}
public_forecasts/{forecastId}
public_receipts/{receiptDigest}
public_reviews/{reviewId}                  # only when not safely embedded

public_catalogs/forecasters__{part}
public_catalogs/models__{part}
public_catalogs/services__{part}
```

Rules:

- deterministic UUIDv5 identifiers remain the same in staging and production;
- iPulse IDs are preserved as source references, not overloaded as every
  Forecast Library object ID;
- immutable version documents are append-only;
- profiles point to `currentVersionId`, while receipts point to the exact
  historical version;
- public catalog documents contain compact projections and split before the
  established safe byte threshold;
- profile/detail pages read one detail record plus the latest materialized
  catalog parts rather than joining many Firestore documents in the browser;
- secret service configuration and credentials remain in Secret Manager or the
  controlled backend, never Firestore public collections.

## Standards alignment

- Agent2Agent Protocol 1.0 specification: https://a2a-protocol.org/latest/specification/
- A2A core concepts: https://a2a-protocol.org/latest/topics/key-concepts/
- Model Cards for Model Reporting: https://research.google/pubs/model-cards-for-model-reporting/
- JSON Canonicalization Scheme (RFC 8785): https://www.rfc-editor.org/rfc/rfc8785

The A2A specification allows Agent Cards to be JWS-signed after RFC 8785
canonicalization. Forecast Library should verify and preserve that signature
when present, while still calculating its own SHA-256 snapshot digest for
receipt provenance and long-term resolution.
