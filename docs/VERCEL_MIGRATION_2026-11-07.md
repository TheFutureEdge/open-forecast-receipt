## Source and release route

GitHub CI remains required before candidate release. Its tests cover receipt
digests, schemas, EAS encoding, tamper detection, permanent routes and identity
separation. Build without Firestore reads; public page and receipt ISR is
generated on demand with a five-minute revalidation interval. The sitemap
continues to read bounded catalogs at request time.

Use the existing selected-repository Vercel GitHub App installation, with only
TheFutureEdge/open-forecast-receipt added for this migration. Keep both existing
Vercel projects and their environment profiles. Do not create replacement
projects or enable organization-wide repository access.

The automatic release contract is:

- forecast-library-staging: Production Branch is staging; its technical
  production deployments use the staging Firebase project and staging origin.
- forecast-library-production: Production Branch is main; its technical
  production deployments use the production Firebase project and public origin.
- Keep preview deployments disabled and preserve deployment protection.
- Use npm ci, npm run build and Node 22. The repository's vercel.json is the
  canonical build configuration; the source-file bootstrap is a fallback only.
- Require the existing GitHub Actions verify check before production alias
  assignment. Keep automatic aliasing enabled so passing Git builds release
  without manual CLI promotion. Never force-promote past a failed check.
- Use feature PR -> staging, validate the exact staging deployment, then merge
  staging -> main and verify the exact automatically deployed production commit.

If native Git integration is unavailable, use the authenticated Vercel
connector and source-file deployments generated by
scripts/operations/vercel-source-files.mjs EXACT_REVIEWED_SHA. The bootstrap
fetches only TheFutureEdge/open-forecast-receipt at that exact public commit,
verifies FETCH_HEAD, then checks out and installs the committed lockfile.
Record the exact commit in deployment metadata and retain build-log proof.
Local .env files and credentials are never uploaded.

The existing gh Keychain credential can administer the repository. GitHub App
installation endpoints require an app-authorized token; a 403 there does not
prove missing organization-admin access. Use the installation's normal GitHub
settings flow and owner authentication when needed. Do not regenerate working
GitHub credentials or store new deployment tokens for this integration.

The user's migration authorization covers focused commits, pushes, release
branches, CI, candidate deployments and the scoped infrastructure above.
Do not issue new attestations or publish new forecast data for a hosting test.

## Public DNS and rollback

Both apex and www are attached and ownership-verified on the production
Vercel project. Public DNS now serves Vercel through A 216.150.1.1 and
A 216.150.16.1 at both @ and www, with TTL 3600. The old serving A value was
35.219.200.13. Preserve NS, MX, TXT, certificate, DNSSEC and all unrelated records.
The www host already has a Firebase claim TXT, so retain A records there rather
than replacing them with an incompatible CNAME.

Both authoritative nameservers and Cloudflare/Google DNS confirmed the new
records. An auto-renewing certificate covers the apex and www. Trusted HTTPS,
the www-to-apex redirect and HTTP-to-HTTPS upgrades passed with path/query
preservation. No certificate validation was bypassed.
To roll back the initial cutover, remove both Vercel A values at each name,
restore both names to A 35.219.200.13 and verify the retained Firebase service.
DNS rollback has resolver delay.

Allow 24-48 hours of observation before a separately reviewed retirement of
the old frontends. Confirm there are no publication callbacks, tagged serving
revisions or automatic rollouts that depend on them before disabling them.
Keep Firestore, backups and the public receipt identity contract intact.
